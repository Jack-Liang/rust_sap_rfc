# Server 端实现：SAP → HTTP 反向代理

## 目标
让 SAP 系统通过 RFC 回调本服务，本服务把入站调用转发到配置的 HTTP webhook，再把 webhook 响应回填给 SAP。与现有 client（HTTP→SAP）方向对称。

## 决策汇总
- 函数暴露方式：**配置驱动的 webhook 转发**
- SM59 配置：用户自己负责
- API 选择：**旧 API**（RegisterServer + ListenAndDispatch），Rust 掌控 dispatch 线程

## 工作原理

```
[SAP 系统]
   │ 1. SM59 配 RFC Destination (Type T, Registration mode)
   │    Program ID = ZREST_SERVER (与配置一致)
   ↓ 2. SAP 调用 CALL FUNCTION 'Z_GET_DATA' DESTINATION 'ZREST'
[本服务: RfcListenAndDispatch 循环]
   │ 3. 收到调用，匹配到 Z_GET_DATA 的回调
   │ 4. 回调内：读 SAP 入参 → POST 到配置的 webhook URL
   │ 5. 等 webhook 响应 → 把响应字段回填 funcHandle
   ↓ 6. 返回 RFC_OK，SAP 拿到 EXPORTING 参数
[配置的 webhook 服务 (任意语言)]
   收到 {func, inputs} → 处理 → 返回 {outputs}
```

## servers.toml 配置格式

```toml
# Gateway 连接（从 SAP 系统注册）
[gateway]
gwhost = "host.docker.internal"   # SAP gateway 主机（a4h 容器）
gwserv = "sapgw00"                # gateway 服务（sysnr 00 → sapgw00）
program_id = "ZREST_SERVER"       # 必须与 SM59 的 Program ID 一致

# 对外暴露的 RFC 函数定义
[[functions]]
name = "Z_REST_PROXY"             # SAP 调用的函数名
# webhook：收到调用时 POST 到此 URL
webhook_url = "http://localhost:9000/handle"
# 函数的参数定义（用于 SDK 注册元数据）
[[functions.params]]
name = "REQUTEXT"
direction = "import"              # import/export/changing/tables
type = "char"
length = 255
[[functions.params]]
name = "RESPTEXT"
direction = "export"
type = "char"
length = 1024
```

## server_rfc.rs 核心设计

### 1. 启动流程
```
load servers.toml →
  对每个 function：RfcCreateFunctionDesc + RfcAddParameter 构造元数据 →
  RfcInstallServerFunction(注册回调) →
  RfcRegisterServer(gwhost/gwserv/program_id) →
  循环 RfcListenAndDispatch(handle, timeout=5)
```

### 2. dispatch 循环（专用 std::thread，非 tokio）
```rust
// 在独立 OS 线程跑（FFI 阻塞调用，不能在 tokio worker）
std::thread::spawn(move || loop {
    let rc = RfcListenAndDispatch(handle, 5, &mut err);  // 5s 超时
    match rc {
        RFC_OK => { tracing::debug!("一次调用处理完成"); }
        RFC_RETRY => continue,  // 超时无调用，继续
        RFC_CLOSED => break,    // gateway 断开
        _ => { tracing::error!(rc, "dispatch 错误"); break; }
    }
});
```

### 3. 回调函数（extern "system"，可被 C 调用）
```rust
// 全局：函数名 → WebhookConfig 映射（启动时填充）
static HANDLERS: OnceLock<Mutex<HashMap<String, WebhookConfig>>> = ...;

extern "system" fn generic_handler(
    _rfc_handle: RFC_CONNECTION_HANDLE,
    func_handle: RFC_FUNCTION_HANDLE,
    err: *mut RFC_ERROR_INFO,
) -> RFC_RC {
    // 1. 从 func_handle 拉函数名（RfcGetFunctionName）
    // 2. 查 HANDLERS 拿到 webhook_url + 参数定义
    // 3. 遍历 import 参数，读出值 → 组装 JSON {func, inputs}
    // 4. reqwest::blocking::post(webhook_url).json(...)  ← 同步 HTTP
    // 5. 解析响应 → 遍历 export 参数，用 set_chars/set_int 回填 func_handle
    // 6. 返回 RFC_OK（或失败时填 err 返回 RFC_EXTERNAL_FAILURE）
}
```

### 4. FFI 新增绑定
- `RfcRegisterServer`、`RfcListenAndDispatch`、`RfcInstallServerFunction`
- `RfcCreateFunctionDesc`、`RfcAddParameter`
- `RfcGetFunctionName`（回调里取函数名）
- RFC_RC 常量（RFC_RETRY 等）
- RFC_DIRECTION 值（RFC_IMPORT=1/Export=2/...）

### 5. 复用现有代码
- **function.rs 完全复用**：回调里收到的 `RFC_FUNCTION_HANDLE` 与 client 的同类型，`RfcFunction` 的 `get_chars/set_chars/get_int/...` 直接可用
- **string_utils.rs**：UC 转换
- **error.rs**：check_rc

## main.rs 改造
根据环境变量 `SAP_ROLE`（或配置存在性）决定模式：
- `SAP_ROLE=client`（默认）：仅启动现有 HTTP server
- `SAP_ROLE=server`：仅启动 SAP server（dispatch 循环）
- `SAP_ROLE=both`：两个都启（client HTTP + server dispatch 各自独立线程/任务）

## 关键技术难点与对策

| 难点 | 对策 |
|---|---|
| 回调是 C→Rust，签名必须 `extern "system"` | 用 `extern "system" fn`，`#[unsafe(no_mangle)]` 不需要（传函数指针而非导出符号）|
| 回调里发 HTTP 必须**同步**（dispatch 线程阻塞等结果） | 用 `reqwest::blocking`，在 std::thread 内 |
| 全局 HANDLERS 映射 | `OnceLock<Mutex<HashMap>>`，启动时写一次，回调时只读 |
| 函数名从 func_handle 获取 | `RfcGetFunctionName` |
| webhook 超时/失败如何回传 SAP | 填 `RFC_ERROR_INFO.message`，返回 `RFC_EXTERNAL_FAILURE` |
| 优雅停机 | 停 dispatch 线程（gateway 断开即退出循环），`RfcShutdownServer` 不适用旧 API |

## 限制说明（写入文档）
- **无状态**：每个 SAP 调用独立处理，不维护 stateful session（首版）
- **串行**：dispatch 单线程，SAP 并发调用排队（首版简化；可后续多线程 dispatch）
- **不支持 tRFC/qRFC**：事务回调首版不实现
- **webhook 必须返回及时**：SAP 侧有 RFC 超时，webhook 慢会导致 SAP 端超时
